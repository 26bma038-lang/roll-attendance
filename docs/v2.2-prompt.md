## Phase 3 — Academic notices from the NITH website

Only **academic** notices, not recruitment, tenders, faculty or alumni notices.

**Pages to read** (checked 2026-11-07; each is a plain HTML table `Sl. No. | Particulars`, every row
one link, usually to a PDF under `https://nith.ac.in/uploads/files/...`, **no dates shown**, and
the same row can appear twice):

| Page | Category in Roll |
|---|---|
| `https://nith.ac.in/academic-notices` | Academic |
| `https://nith.ac.in/examination-schedules` | Exams |
| `https://nith.ac.in/student-related-notices` | Students — keep only rows that match the academic filter below |

Academic filter for the student page (case-insensitive keywords in the title): exam, examination,
date sheet, datesheet, result, academic, calendar, semester, registration, classes, timetable,
time table, scholarship, fee, holiday, suspension, attendance, re-appear, backlog. Keep the list in
a config file with unit tests. Store everything from the first two pages.

**New tool `tools/nith-notices/`** (Node 20, same style as `classroom-sync`):
- Fetch each page with a normal browser-like User-Agent naming the app (`RollApp/2.2`), one request
  per page, a 20 s timeout. Parse the table rows: title (whitespace collapsed) + absolute URL.
- De-duplicate by URL. Notice id = hash of the URL.
- **Date:** the site shows none. Use the month folder in the URL when present
  (`/uploads/files/oct26/` → October 2026), otherwise `firstSeenAt` (when the sync first saw it).
  Sort newest first.
- Write `collegeFeed/nith` as ONE document (like `materialSources`, one read per student):
  `{ syncedAt, items: [{ id, title, url, category, monthLabel?, firstSeenAt }] }`, keeping the
  newest 150. Only write when something changed.
- If a page fails or its table can't be found, don't wipe existing items: keep the old ones, log a
  clear error, and fail the job (GitHub emails the user). Tests: parser on saved HTML fixtures of
  all three pages, the dedupe, the month parsing, the filter, and "page broke → nothing deleted".
- `--dry-run` prints what it found; `npm run sync` writes.
- GitHub Actions: `.github/workflows/nith-notices.yml`, every 3 hours from 08:00 to 20:00 IST plus
  manual dispatch. Reuses `FIREBASE_SERVICE_ACCOUNT`.

**Rules:** `collegeFeed/{id}`: read if `validUser()`, no client writes. Rules tests like
`materialSources`.

**App:** show these in the existing **college notices** screen (from v2 Phase 5) as a second
section/filter, "From nith.ac.in", with category chips Academic / Exams / Students. Each row: title,
month label in IBM Plex Mono, tap → open the PDF/link (ACTION_VIEW). Keep the admin's own college

**Notifications:** if the app already has FCM, send a push for new **Exams** and **Academic** items

If it has no FCM, skip push: show the new items in the app only, and say so.

## Phase 4 — An app that doesn't feel empty

1. **First-year subjects ready on day one.** A first-year class whose CRs haven't added subjects
   yet gets its subject list pre-filled from the study material's subject codes and names
   (MA-111 Eng. Mathematics-1, PH-101 Engineering Physics …), plus the lab codes. A CR can edit or
   remove them. Do it once per class, when the first CR opens Manage, with a confirm step
   ("Add the 14 first-year subjects?"), not silently.
2. **Empty states that say what to do**, in the §6 voice, on every screen that can be empty:
   Today with no classes and no CR ("Your class has no CR yet. The admin appoints one."), no
   timetable ("Your CR hasn't set up the timetable yet."), no deadlines, no notices, Department
   with nobody marked. Where a next step exists, give it a button (CR: "Set up timetable").
3. **Today shows something useful even with no classes:** the latest 3 NITH academic notices and
   the next deadline, below the empty message.

## Phase 5 — Timetable from the college's PDF

The college sends the timetable as a PDF. Turn it into Roll's subjects + weekly timetable slots
without hand entry, and still stay on Spark: an **admin-run tool**, not an in-app upload.

**Zero cost: the user cannot spend any money.** Use only free tiers, with no billing account or card
anywhere.

- `tools/timetable-import/` (Node 20). `npm run extract -- path/to/timetable.pdf` sends the PDF to
  the **Google Gemini API free tier** (key from Google AI Studio, aistudio.google.com → Get API key,
  no billing; use the current free "Flash" model and check its exact name in AI Studio; key in
  `.secrets/gemini-key` or the env var `GEMINI_API_KEY`, never committed). The free tier has
  per-minute and per-day limits: one PDF is one request, so retry with backoff on HTTP 429 and
  explain the limit in plain words if it is hit. Free-tier inputs may be used by Google to improve
  its models; a timetable has no personal data, but never send anything that does. Ask for strict
  JSON (use the API's JSON response mode with a schema): per class (batch + branch, or
  section if the PDF uses sections), the subjects (code, name, type lecture/lab/tutorial) and weekly
  slots (day, start, end, subject code, room). One PDF may cover many branches: extract all of them.
- It writes `timetable-draft.json` and prints a readable table per class. **Nothing is written to
  Firestore yet.** The admin checks and edits the JSON by hand.
- `npm run apply -- timetable-draft.json` writes subjects + timetable slots for each class that
  exists, using the same Firestore shape the app's Manage screens write. It shows a summary first
  and asks `y/N`. It never deletes slots a CR added by hand unless `--replace` is passed.
- **Fallback without any AI:** if the PDF has real text (not a scan), also offer
  `npm run extract -- --no-ai file.pdf`, which reads the table with `pdfjs-dist` and rules. It may
  need more hand-fixing, but it works if the free tier is down or the limit is hit.
- Ask the user for a real timetable PDF before building the prompt and parser, and save it as a
  test fixture only if it has no personal data. Unit-test the JSON validation (overlapping slots,
  unknown days, end before start, subject codes missing from the subject list).
